Jira Claude Worker - Full Worker Integration Contract
=====================================================

Audience
--------
This document is written for a local LLM or engineer that needs to replace the placeholder worker
with a real Jira/Git/Claude automation worker while keeping the existing FastAPI website working.

The website is the main UI. The worker is the backend automation engine behind the UI.

The local LLM should treat this file as the source of truth for:

- what data the website expects,
- what methods the real worker must expose,
- what database rows must be written,
- what states mean,
- how progress and logs are shown,
- what Git and Claude are allowed to do,
- and how the website buttons map to worker behavior.


0. Current Project Shape
------------------------
Important files:

    app/web.py
        FastAPI routes and UI action handlers.

    app/db.py
        SQLite schema and helper methods.

    app/runner.py
        Placeholder worker implementation.

    app/templates/
        HTMX/Jinja UI templates.

    app/static/
        UI JavaScript and CSS.

    config.yaml
        Local runtime config. This file is intentionally not committed.

    config.example.yaml
        Example config committed to Git.

The real worker may replace app/runner.py or be wrapped by app/runner.py, but it should not require
template changes unless the UI itself is intentionally changed.


1. High-Level Responsibility Split
----------------------------------
The website is responsible for:

- Displaying current run status.
- Displaying ticket number, ticket name, and short ticket description for active runs.
- Displaying live logs.
- Displaying queue, skipped tickets, manually runnable tickets, and completed runs.
- Letting the user scan Jira, run once, start interval mode, stop interval mode, reorder queue,
  enqueue a ticket, rerun a ticket, cancel current run, run CR fix, push branch, and edit config.
- Editing config visually and as raw YAML.

The worker is responsible for:

- Scanning Jira.
- Deciding ticket eligibility.
- Creating/updating ticket rows.
- Creating queue rows for eligible tickets.
- Running the next queued ticket.
- Creating/updating run rows.
- Writing logs.
- Updating progress.
- Calling Claude.
- Performing all Git operations.
- Canceling an active run.
- Running CR fix.
- Pushing finished branches.

Claude is responsible for:

- Understanding the ticket.
- Proposing repo/base branch/branch summary when asked.
- Implementing code changes.
- Reviewing code changes.
- Optionally fixing review findings.

Claude is NOT responsible for:

- cloning,
- fetching,
- checking out,
- creating branches,
- committing,
- rebasing,
- merging,
- pushing,
- resetting,
- or any other Git command.

Python worker owns all Git interactions.

4. Table: tickets
-----------------
Purpose:

    Stores Jira ticket metadata and eligibility information.

Schema:

    key TEXT PRIMARY KEY
    summary TEXT NOT NULL
    status TEXT NOT NULL
    url TEXT NOT NULL DEFAULT ''
    description TEXT NOT NULL DEFAULT ''
    labels TEXT NOT NULL DEFAULT ''
    eligibility TEXT NOT NULL DEFAULT 'discovered'
    skip_reason TEXT NOT NULL DEFAULT ''
    last_seen_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP

Field meaning:

    key
        Jira issue key. Example: ABC-123.

    summary
        Jira issue title. This is displayed as the ticket name.

    status
        Jira workflow status text. Example: To Do, In Progress, Review, Done.

    url
        Browser URL for the Jira ticket.

    description
        Plain text ticket body plus useful comment text. The active run panel shows the first
        part of this field as the small description.

    labels
        Comma-separated labels. Example: backend,urgent,claude.

    eligibility
        One of:
            discovered
            eligible
            skipped

    skip_reason
        Human-readable reason why the ticket was not auto-queued. Empty string when eligible.

Required behavior during Jira scan:

1. Fetch assigned Jira tickets according to config.
2. Convert Jira rich text to plain text.
3. Upsert each ticket row.
4. Set eligibility and skip_reason.
5. Auto-enqueue eligible tickets.

Default eligibility rules:

    eligible:
        Ticket is assigned to the configured/current Jira user and status is not excluded.

    skipped:
        Ticket status is in jira.excluded_statuses.
        skip_reason example: status is Done

    skipped:
        jira.required_text is non-empty and the text is missing from title/description/labels.
        skip_reason example: missing required text "for claude"

    discovered:
        Use only if the worker has seen the ticket but has not classified it yet.

Important UI behavior:

- Manual Ticket Selection shows non-eligible tickets from this table.
- User can manually enqueue skipped/non-eligible tickets.
- Active run displays ticket key, summary, status, and description.


5. Table: queue_items
---------------------
Purpose:

    Stores ticket execution queue and priority order.

Schema:

    id INTEGER PRIMARY KEY AUTOINCREMENT
    ticket_key TEXT NOT NULL
    priority INTEGER NOT NULL DEFAULT 0
    state TEXT NOT NULL DEFAULT 'queued'
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP

Field meaning:

    ticket_key
        Jira issue key. Must match tickets.key.

    priority
        Lower number runs first. The website drag reorder updates this field.

    state
        queued
        running
        done
        failed
        cancelled

Queue selection rule:

    SELECT the queued item with lowest priority, then lowest id.

Required worker behavior:

- Do not create duplicate active queue rows for the same ticket_key where state is queued/running.
- When a run starts, set queue_items.state = running.
- When a run completes successfully, set queue_items.state = done.
- When a run fails, set queue_items.state = failed.
- When a run is cancelled, set queue_items.state = cancelled.
- Do not change queue priority while executing unless explicitly implementing a new feature.

Website routes that touch queue_items:

    POST /queue/reorder
        Updates priority.

    POST /tickets/{ticket_key}/enqueue
        Inserts a queued item.

    POST /tickets/{ticket_key}/rerun
        Inserts a new queued item if none is already queued/running.


6. Table: runs
--------------
Purpose:

    Stores each automation attempt/run.

Schema:

    id INTEGER PRIMARY KEY AUTOINCREMENT
    ticket_key TEXT NOT NULL
    state TEXT NOT NULL DEFAULT 'queued'
    progress INTEGER NOT NULL DEFAULT 0
    repo_url TEXT NOT NULL DEFAULT ''
    base_branch TEXT NOT NULL DEFAULT ''
    branch_name TEXT NOT NULL DEFAULT ''
    workspace_path TEXT NOT NULL DEFAULT ''
    review_output TEXT NOT NULL DEFAULT ''
    error TEXT NOT NULL DEFAULT ''
    pushed_at TEXT
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    finished_at TEXT

Field meaning:

    ticket_key
        Jira issue key.

    state
        Current run state. The UI uses this heavily.

    progress
        Integer from 0 to 100. The UI displays this as the progress bar.

    repo_url
        Git clone URL selected for the ticket.

    base_branch
        Base branch selected for ticket work. Example: main, develop.

    branch_name
        Final feature branch name created by Python.

    workspace_path
        Local path where this ticket was cloned.

    review_output
        Review agent output. Used for CR-fix context and visible in history.

    error
        Failure/cancel reason if any.

    pushed_at
        Timestamp when branch was pushed.

    finished_at
        Timestamp when run reached done, failed, or cancelled.

Supported run states:

    queued
    preparing_git
    running_claude
    reviewing
    needs_cr_fix
    done
    failed
    cancelled
    pushed

Legacy/planned states accepted by contract but not currently displayed as active:

    discovered
    skipped

Active run states shown in Current Run panel:

    preparing_git
    running_claude
    reviewing

Finished Runs panel states:

    done
    needs_cr_fix
    pushed
    failed
    cancelled

Recommended state transition for normal run:

    queued
      -> preparing_git
      -> running_claude
      -> reviewing
      -> needs_cr_fix OR done

If review is only informational:

    reviewing -> done

If review finds issues and user should decide:

    reviewing -> needs_cr_fix

If user clicks Do CR Fix:

    needs_cr_fix
      -> running_claude
      -> reviewing
      -> done

If user clicks Push:

    done OR needs_cr_fix
      -> pushed

If run fails:

    any active state -> failed

If user cancels:

    any active state -> cancelled

Recommended progress ranges:

    0-5       Run row created
    5-15      Claude discovery of repo/base/branch summary
    15-25     Git clone/fetch/checkout/branch creation
    25-80     Main Claude implementation
    80-95     Review agent
    95-100    CR fix/finalization/push-ready

Important:

- progress must be clamped between 0 and 100.
- progress should only move backward if a new phase intentionally restarts work.
- set finished_at when state becomes done, failed, or cancelled.
- set pushed_at when state becomes pushed.


7. Table: logs
--------------
Purpose:

    Stores live terminal/event output for runs.

Schema:

    id INTEGER PRIMARY KEY AUTOINCREMENT
    run_id INTEGER NOT NULL
    phase TEXT NOT NULL
    line TEXT NOT NULL
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP

Field meaning:

    run_id
        runs.id.

    phase
        Short label for source/stage.

    line
        One log line. Should not include trailing newline.

Recommended phases:

    jira
    discover
    git
    claude
    review
    cr-fix
    push
    system
    error

Live output behavior:

- Insert logs while the work is running, not only after the process exits.
- The dashboard polls every 2 seconds.
- Current Run panel shows latest logs from this table.
- GET /runs/{run_id}/logs returns all logs as plain text.

Secret rule:

- Never insert raw secrets into logs.
- Mask known tokens before inserting logs.
- Suggested mask value: ***

Progress from logs:

- If Claude prints lines like:

      PROGRESS 40%

  the worker may parse that and update runs.progress to 40.

- This is optional but recommended.


7A. Agent Questions, User Input, And Sub-Agent Tables
-----------------------------------------------------
These tables let the worker interact with the user while a ticket is running.

The website already supports:

- showing questions from the agent,
- letting the user choose one of 3 options,
- letting the user type a free custom answer,
- letting the user send extra instructions mid-run,
- showing sub-agents summoned by the main agent,
- and opening a focused run page for one ticket.


Table: agent_questions
----------------------
Purpose:

    Stores questions that the main agent or a sub-agent asks the user during a run.

Schema:

    id INTEGER PRIMARY KEY AUTOINCREMENT
    run_id INTEGER NOT NULL
    agent_name TEXT NOT NULL DEFAULT 'main'
    question TEXT NOT NULL
    option_a TEXT NOT NULL
    option_b TEXT NOT NULL
    option_c TEXT NOT NULL
    free_input_enabled INTEGER NOT NULL DEFAULT 1
    state TEXT NOT NULL DEFAULT 'pending'
    answer TEXT NOT NULL DEFAULT ''
    answer_source TEXT NOT NULL DEFAULT ''
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    answered_at TEXT

Worker behavior:

- Insert a row when the agent needs user input.
- Always provide exactly 3 option strings:

      option_a
      option_b
      option_c

- Set free_input_enabled = 1 if the user may write a custom answer.
- Set state = pending when asking.
- Pause or periodically wait for the answer if the decision blocks the agent.
- Continue automatically when state becomes answered.
- Read answer and answer_source.

Website behavior:

- Pending questions appear on the focused run page.
- The user can select one of the 3 options.
- The user can also type a custom free answer.
- If both option and free answer are provided, free answer wins.
- On submit, the website sets:

      state = answered
      answer = selected/custom answer
      answer_source = option OR free_input
      answered_at = current timestamp

Recommended worker polling query:

    SELECT * FROM agent_questions
    WHERE run_id = ? AND state = 'answered'
    ORDER BY answered_at

Recommended blocking loop:

    1. Insert pending question.
    2. Log that the agent is waiting for user input.
    3. Poll agent_questions.id every 2-5 seconds.
    4. When answered, send the answer back into the agent process or next prompt.
    5. Log the selected answer in a non-secret-safe way.


Table: agent_inputs
-------------------
Purpose:

    Stores mid-run user messages that are not answers to a specific question.

Schema:

    id INTEGER PRIMARY KEY AUTOINCREMENT
    run_id INTEGER NOT NULL
    message TEXT NOT NULL
    consumed INTEGER NOT NULL DEFAULT 0
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    consumed_at TEXT

Website behavior:

- Focused run page has a "Message during run" input.
- When the user submits text, the website inserts agent_inputs row.
- The website also writes a user log line.

Worker behavior:

- Poll for unconsumed input while the agent is running:

      SELECT * FROM agent_inputs
      WHERE run_id = ? AND consumed = 0
      ORDER BY id

- Deliver each message to the agent if possible.
- Mark consumed = 1 and consumed_at = current timestamp after delivering.
- If live delivery is not technically possible with the current Claude process, include the message
  in the next Claude prompt or next phase.

Important:

- Do not ignore agent_inputs silently.
- If an input cannot be delivered immediately, log that it will be used in the next phase.


Table: sub_agents
-----------------
Purpose:

    Stores sub-agents summoned by the main agent so the user can see them in the UI.

Schema:

    id INTEGER PRIMARY KEY AUTOINCREMENT
    run_id INTEGER NOT NULL
    name TEXT NOT NULL
    task TEXT NOT NULL DEFAULT ''
    status TEXT NOT NULL DEFAULT 'starting'
    progress INTEGER NOT NULL DEFAULT 0
    summary TEXT NOT NULL DEFAULT ''
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP

Unique index:

    run_id + name

Field meaning:

    name
        Stable sub-agent name. Example: backend-agent, ui-agent, tests-agent.

    task
        What the sub-agent is doing.

    status
        starting
        running
        blocked
        done
        failed
        cancelled

    progress
        0-100 for this sub-agent only.

    summary
        Short latest status or final result.

Worker behavior:

- When the main agent summons a sub-agent, upsert a sub_agents row.
- Update progress/status while it works.
- If the sub-agent asks a question, insert agent_questions with agent_name = sub-agent name.
- When it finishes, set status = done and progress = 100.
- If it fails, set status = failed and summary = concise failure reason.

Website behavior:

- Dashboard shows a compact strip of active sub-agents for the current run.
- Focused run page shows full sub-agent list.


8. Required Worker Interface
----------------------------
The current app.web.create_app creates:

    worker = Worker(config, db)

Therefore the real Worker class should provide these methods:

    async def scan_jira(self) -> int:
        Scan Jira.
        Upsert tickets.
        Auto-enqueue eligible tickets.
        Return number of scanned tickets.

    async def scan_and_run_once(self) -> None:
        Usually: await scan_jira(); await run_next()

    async def run_interval_forever(self) -> None:
        Loop forever:
            scan_and_run_once()
            sleep config.app.interval_seconds

    def start_interval(self) -> bool:
        Start a background interval task.
        Return False if already running.

    def stop_interval(self) -> None:
        Stop the interval task.

    async def run_next(self) -> int | None:
        Run the next queued ticket.
        Return run_id, or None if no queue item exists or another run is active.

    def cancel_current(self) -> None:
        Cancel the active Claude/process run if one exists.

    async def run_cr_fix(self, run_id: int) -> None:
        Run Claude to fix review findings for the given run.

    def push_run(self, run_id: int) -> str:
        Push the branch for the run.
        Return command output or a short success string.

    def rerun_ticket(self, ticket_key: str) -> None:
        Enqueue the ticket again.

If your real worker uses a different internal shape, create an adapter class with the exact methods above.


9. Website Route Behavior
-------------------------
Routes and expected worker/database effects:

    GET /
        Render dashboard.
        Reads tickets, queue_items, runs, and logs.

    GET /runs/{run_id}
        Render focused run page for one ticket.
        Reads run, ticket, logs, agent_questions, agent_inputs, and sub_agents.
        This is where the user sees the "IDE/workspace" focus panel, all agent questions,
        mid-run inputs, and sub-agent activity.

    POST /jira/scan
        Calls await worker.scan_jira().
        Expected DB effect:
            tickets table updated.
            eligible tickets may be added to queue_items.

    POST /queue/run-once
        Starts worker.run_next() in a background task.
        Expected DB effect:
            next queued item becomes running.
            run row is created.
            logs/progress update over time.

    POST /queue/start-interval
        Calls worker.start_interval().

    POST /queue/stop-interval
        Calls worker.stop_interval().

    POST /queue/reorder
        Website directly updates queue_items.priority.

    POST /tickets/{ticket_key}/enqueue
        Website directly enqueues ticket_key.

    POST /tickets/{ticket_key}/rerun
        Calls worker.rerun_ticket(ticket_key).

    POST /runs/{run_id}/cancel
        Calls worker.cancel_current().
        Website currently sets runs.state = cancelled and runs.error = "cancel requested".
        Better real-worker behavior:
            set state = cancelling first if you add that state,
            stop process,
            then set cancelled/failed based on result.

    POST /runs/{run_id}/review-fix
        Starts worker.run_cr_fix(run_id) in a background task.

    POST /runs/{run_id}/push
        Calls worker.push_run(run_id).

    POST /runs/{run_id}/input
        Website inserts agent_inputs row with the user's mid-run message.
        Website also adds a logs row with phase = user.
        Worker should later consume this row and deliver it to the active agent or next phase.

    POST /agent-questions/{question_id}/answer
        Website answers a pending agent question.
        User can choose option_a, option_b, option_c, or write free input.
        Free input wins if both free input and option are provided.
        Website updates agent_questions.state, answer, answer_source, answered_at.
        Website also adds a logs row with phase = user.

    GET /runs/{run_id}/logs
        Website reads logs table and returns plain text.

    GET /settings
        Render visual config + raw YAML config.

    POST /settings
        Save raw YAML.

    POST /settings/visual
        Save known config fields from visual form and preserve unknown fields.


10. Jira Scan Detailed Behavior
-------------------------------
scan_jira() should:

1. Read Jira config:

       jira.url
       jira.email
       jira.token
       jira.jql
       jira.max_results
       jira.excluded_statuses
       jira.required_text

2. Query Jira.

3. Normalize each issue:

       key
       summary
       status
       url
       description
       labels

4. Classify eligibility.

5. Upsert tickets.

6. Enqueue eligible tickets that do not already have queue_items.state in queued/running.

7. Log scan-level errors in a reasonable place:

       either raise exception for UI flash,
       or create system logs if tied to a run.

No run row is required for a plain Jira scan.


11. Git Detailed Behavior
-------------------------
Python worker must do all Git operations using safe subprocess calls.

Use argument arrays, not shell strings:

    subprocess.run(["git", "clone", clone_url, target_path], ...)

Do not do:

    subprocess.run("git clone " + url + " " + path, shell=True)

Required Git phases:

1. Determine repo_url and base_branch.
   This may come from:
       Claude discovery,
       Jira fields,
       config mapping,
       or your own code.

2. Create one clone per ticket/run.
   Default workspace root:

       config.app.workspace_dir

   Example:

       workspaces/ABC-123

3. Fetch base branch.

4. Checkout base branch.

5. Create feature branch.

Branch name format:

    <ticket-key>/by_claude_<slug-summary>

Example:

    ABC-123/by_claude_fix_login_timeout

Slug rules:

- lowercase
- only a-z, 0-9, underscore
- replace spaces/punctuation with underscore
- collapse repeated underscores
- keep reasonably short, around 48 chars for slug part

6. Write Git metadata into runs:

       repo_url
       base_branch
       branch_name
       workspace_path

7. Push only when user clicks Push.

push_run(run_id) should:

- find run row,
- verify workspace_path and branch_name exist,
- run git push,
- set state = pushed,
- set pushed_at timestamp,
- add a push log line.

Do not auto-push unless the user explicitly adds such a feature.


12. Claude Detailed Behavior
----------------------------
The worker may use Claude CLI or another Claude integration.

Current config supports:

    claude.command
    claude.args
    claude.model
    claude.api_key
    claude.timeout_seconds
    claude.allow_cr_fix
    claude.auto_cr_fix

Discovery prompt should return:

    repo_url
    base_branch
    summary

Recommended JSON:

    {
      "repo_url": "git@gitlab.com:group/project.git",
      "base_branch": "main",
      "summary": "fix login timeout"
    }

Implementation prompt must include:

- Jira key.
- Ticket title.
- Ticket description.
- Current branch.
- Rule: do not run Git commands.
- Rule: Python owns all Git interactions.
- Request progress lines like PROGRESS 40%.
- Permission to spawn subagents if the ticket naturally splits into independent components.

Review prompt must:

- Ask for bugs, regressions, missing tests, incomplete requirements.
- Put findings first.
- Say clearly if there are no findings.
- Forbid Git commands.

CR fix prompt must:

- Include review_output.
- Ask Claude to fix the review findings.
- Forbid Git commands.

Claude output should be streamed line-by-line into logs.


13. Cancellation Behavior
-------------------------
Minimum behavior:

- cancel_current() terminates active Claude/process if any.
- run state becomes cancelled.
- queue item state becomes cancelled.
- error field contains a short reason.
- finished_at is set.

Better behavior:

- Track process object or PID.
- On cancel:
    1. request graceful termination,
    2. wait a short timeout,
    3. force kill if needed,
    4. log what happened.

The current DB does not have a "cancelling" state, but you may add it if you update the UI accordingly.


14. Interval Mode
-----------------
start_interval() should:

- start a background task,
- not start a duplicate task if already running,
- return False if already running.

run_interval_forever() should:

- call scan_and_run_once(),
- sleep config.app.interval_seconds,
- repeat forever until cancelled/stopped.

stop_interval() should:

- cancel or stop the background task.

Recommended behavior:

- If one ticket is already running, interval mode should not start another simultaneous run.
- The worker should use a lock around run_next().

16. Error Handling Rules
------------------------
When a run fails:

1. Insert an error log:

       phase = error
       line = concise failure message

2. Update runs:

       state = failed
       error = concise failure message
       finished_at = current timestamp

3. Update queue_items:

       state = failed

4. Do not delete the workspace automatically on failure.
   The user may need to inspect it.

When Jira scan fails:

- It is acceptable to raise the exception so the website flash shows "Jira scan failed: ...".
- Do not crash the whole web server.

When push fails:

- Do not set pushed_at.
- Do not set state = pushed.
- Add a push/error log if possible.
- Return/raise an error so the website flash can show it.


17. Security Rules
------------------
Never log secrets.

Never print these raw values:

- Jira token.
- Git token.
- Claude API key.
- Any authorization header.
- Any full HTTPS URL with embedded credentials.

Masking example:

    https://user:token@gitlab.com/group/repo.git

Should be logged as:

    https://***@gitlab.com/group/repo.git

or:

    gitlab.com/group/repo.git

Do not expose config.yaml in logs.

The website currently displays config values in the Settings page because this is a local-only app.
If remote access is added later, add authentication first.

19. Minimal Happy Path Example
------------------------------
Assume Jira returns:

    key = ABC-123
    summary = Fix login timeout
    status = To Do
    description = Users get logged out too early...

scan_jira() writes:

    tickets:
      key = ABC-123
      summary = Fix login timeout
      status = To Do
      eligibility = eligible
      skip_reason = ''

scan_jira() enqueues:

    queue_items:
      ticket_key = ABC-123
      priority = next number
      state = queued

run_next() selects queue item and creates:

    runs:
      ticket_key = ABC-123
      state = preparing_git
      progress = 5

Discovery sets:

    repo_url = git@gitlab.com:company/app.git
    base_branch = main
    branch_name = ABC-123/by_claude_fix_login_timeout
    progress = 15

Git phase sets:

    workspace_path = workspaces/ABC-123
    progress = 25

Claude implementation:

    state = running_claude
    progress moves 25 -> 80
    logs inserted continuously

Review:

    state = reviewing
    progress = 85
    review_output is stored

Finish:

    state = done
    progress = 100
    finished_at = timestamp
    queue_items.state = done

User clicks Push:

    git push is run by Python
    runs.state = pushed
    runs.pushed_at = timestamp


20. Common Mistakes To Avoid
----------------------------
Do not:

- Change table names without updating the website.
- Use a run state the UI does not know about unless you update the UI.
- Forget to create a tickets row before creating a run.
- Write logs only at the end; the UI needs mid-run logs.
- Let Claude run Git commands.
- Push automatically.
- Store labels as JSON unless you also update UI/DB expectations.
- Put multiline raw JSON blobs in logs unless they are useful to the user.
- Let a scan create duplicate queued/running items for the same ticket.
- Mark a run done before review_output is saved if review is enabled.
- Delete failed workspaces automatically.
- Log tokens or credentialed Git URLs.
- Ask the user a blocking question only in Claude output; insert agent_questions so it appears in UI.
- Spawn sub-agents without updating sub_agents, because the user asked to see them.
- Ignore agent_inputs rows after the user sends mid-run guidance.


21. Acceptance Checklist
------------------------
The real worker is integrated correctly when all of these are true:

- Settings page still loads.
- Scan Jira fills the tickets table.
- Eligible tickets appear in Queue.
- Skipped tickets show skip reasons.
- Manual add works for skipped/non-eligible tickets.
- Queue reorder changes priority.
- Run once starts exactly one ticket.
- Current Run shows ticket key, name, status, short description, progress, branch, and logs.
- Focus ticket opens /runs/{run_id}.
- Focused run page shows questions, mid-run input, sub-agents, workspace, and logs.
- Agent can create a question with exactly 3 options and optional free input.
- User can answer an agent question from the focused run page.
- User can send extra input mid-run from the focused run page.
- Worker consumes agent_inputs rows or logs why delivery is delayed.
- Main agent/sub-agents are visible in sub_agents while they run.
- Logs appear during execution, not only after execution.
- Progress changes during execution.
- Cancel stops active work and marks cancelled.
- Finished runs appear in history.
- Rerun works.
- Review output is saved.
- Do CR Fix works when enabled.
- Push button pushes branch and marks pushed.
- Failed runs show a clear error.
- No secrets appear in logs.
- Tests pass.
